================================================================================
1. WHAT WE BUILT (ONE PARAGRAPH FOR THE INTRODUCTION)
================================================================================

We extend gem5-SALAM with two side-by-side protection mechanisms that gate an
accelerator's access to system memory:

  * AIA-KD  -- a SOFTWARE validator. The host OS kernel "validates" the first
              touch of every 4 KiB page; subsequent accesses to the same page
              by the same process are free. Cost is a per-page first-touch
              tax modelled as an interrupt-driven kernel-driver round-trip.
  * IOMMU   -- a HARDWARE translator. Every memory transaction the
              accelerator emits crosses a shared SMMU and pays an IOTLB
              lookup (hit) or page-table walk (miss) on the response path.

The two mechanisms are mutually exclusive in any single run; `plain` is the
unprotected baseline. Functionality always succeeds in both modes -- only the
TIMING of the protection check is modelled. The simulated platform is gem5's
ARM VExpress_GEM5_V1, DerivO3CPU + DDR4_2400_8x8 + L1/L2 caches, identical
across modes; tick base = 1 ps.

KEY INSIGHT (the comparison's reason to exist):
  AIA-KD pays once PER PAGE; IOMMU pays once PER ACCESS.
  -> AIA-KD wins on access-heavy workloads with small page footprints.
  -> IOMMU wins on workloads with cold-page churn / one-shot accesses.

================================================================================
3. SIMOBJECT LAYOUT (FOR THE IMPLEMENTATION SECTION)
================================================================================

gem5-SALAM groups accelerators into one or more `AccCluster`s. Each cluster
gets EXACTLY ONE shared instance of each protection SimObject:

  AccCluster (one per cluster)
    |
    +-- iommu     : AcceleratorIommu       <- shared IOTLB, chip-wide port
    |                                         deadline, IommuStats group
    |     wired into:  every CommInterface   (acc.iommu = clstr.iommu)
    |     wired into:  every LLVMInterface   (for stats reporting only)
    |
    +-- validator : AiaKdValidator         <- shared validated-pages cache,
    |                                         pending-page set, waiter
    |                                         queue, chip-wide FIFO + one
    |                                         response event
    |     wired into:  every LLVMInterface   (AccConfig(... validator=...))
    |
    +-- accel_0, accel_1, ...               (each: 1x LLVMInterface + 1x CommInterface)

Generation is automatic: tools/SALAM-Configurator/config_parser.py emits the
two `clstr.iommu = AcceleratorIommu(...)` and `clstr.validator =
AiaKdValidator(...)` lines into the generated configs/SALAM/AccCluster.py, and
the per-accelerator wiring lines.

Two SimObjects per cluster for two reasons:
  1. Multi-cluster simulations (mobilenetv2) need per-cluster scoping. A
     single process-wide static would silently leak state across unrelated
     clusters.
  2. Stats are emitted under each SimObject's name in stats.txt
     (system.acccluster_<name>.iommu.*, system.acccluster_<name>.validator.*).

LLVMInterface = the accelerator's compute engine (LLVM-IR scheduler). It
hosts AIA-KD per-CU bookkeeping (reservation queue replay, RAW hazard
re-check, per-CU stats).
CommInterface = the accelerator's memory frontend (3 ports: MemSidePort to
DRAM, SPMPort to scratchpad, RegPort to register banks). It hosts the IOMMU
response-path latency hook.


================================================================================
4. AIA-KD APPROACH -- HOW IT WORKS, WHERE OVERHEAD IS INJECTED
================================================================================

CONCEPT
-------
A software-defined isolation policy where the host OS kernel validates every
unique memory PAGE an accelerator intends to touch BEFORE the access is
allowed to commit. The accelerator stalls the offending memory instruction,
raises a GIC IRQ to the host, the kernel "validates" the page (functionally a
no-op in our model -- we only measure the IRQ + driver round-trip), and the
page is then cached in `validatedPagesPerProcess[PID]` on the cluster's
AiaKdValidator. Subsequent accesses to that page by the same process are
zero-cost cache hits.

STATE (lives on AiaKdValidator, public so LLVMInterface can mutate)
-------------------------------------------------------------------
  validatedPagesPerProcess[pid] : set<pageAddr>   -- the validated-page cache
  pendingValidationPages        : set<pageAddr>   -- in-flight pages
  waitingForPage[pageAddr]      : list<waiter>    -- coalesced followers
  pendingRequests : deque<PendingRequest>          -- chip-wide FIFO of cold misses
  responseEvent   : EventFunctionWrapper           -- one timer per cluster

PER-CU STATE (stays on LLVMInterface)
-------------------------------------
  pendingValidationUIDs                            -- fast-path skip set
  revalidatedUIDs                                  -- mark replayed UIDs to
                                                      avoid double-counting
  per-CU stats counters (validatedPagesCount, ...)

PER-ACCESS PROTOCOL  (src/hwacc/llvm_interface.cc)
--------------------------------------------------
At each Load/Store the per-cluster validator is consulted with the access's
4 KiB page address. Three cases, evaluated in order:

  (a) Cache HIT  -- isPageValidated(page) is true for this PID.
                    Cost = 0 ticks. Fall through to launchRead/launchWrite.

  (b) Pending    -- isPageValidationPending(page).
                    Append the instruction to validator->waitingForPage[page]
                    via queueWaitingInstruction(); the instruction stays in
                    its CU's reservation queue. NO new IRQ, NO duplicate
                    cost. When the in-flight request completes, the validator
                    fans out and replays this waiter through its OWN CU's
                    scheduler. Wait latency is recorded as
                    `validationCoalescedWaits` on the WAITER's CU.

  (c) Cold MISS  -- sendValidationRequest():
                      1. Mark `pendingValidationPages.insert(page)` so
                         simultaneous sibling-CU touches coalesce on (b).
                      2. Build a PendingRequest (carries `cu`, `func`, addr,
                         pid, requestTime) and call validator->enqueue(req).
                      3. The validator schedules its single chip-wide
                         responseEvent for `head.requestTime + latency()`.
                         If already scheduled, the existing schedule
                         covers the new entry (FIFO discipline).
                      4. (Real GIC IRQ raise is INTENTIONALLY suppressed --
                         see "modelling caveats" below.)

When responseEvent fires, AiaKdValidator::processResponse() drains all ready
entries: marks the page validated, removes from pendingValidationPages, then
calls cu->completeValidation(req, now) on the originator. completeValidation
performs a RAW re-check (an instruction may have appeared during the wait)
and either re-issues launchRead/launchWrite or re-queues onto the reservation
list with `revalidatedUIDs.insert(uid)`. The waiter fan-out replays every
entry of waitingForPage[page] through `waiting.func->owner` (the WAITER's CU,
not the originator's).

CHIP-WIDE FIFO INVARIANT
------------------------
The validator's responseEvent is single-shot per cluster: at most ONE IRQ in
flight per cluster at any wall-clock time. This models a single
kernel-driver thread fielding one IRQ at a time. Sibling CUs' cold misses on
DIFFERENT pages serialize through this FIFO; cold misses on the SAME page
coalesce on waitingForPage[page] (free).

WHERE THE OVERHEAD ACTUALLY LANDS IN sim_ticks
----------------------------------------------
The validator's responseEvent is a real gem5 EventFunctionWrapper scheduled
on the event queue. From the moment a cold miss enters the FIFO until
processResponse() fires `latency()` ticks later, the originating
instruction's launchRead/launchWrite is NOT issued. The accelerator's
LLVMInterface stalls that instruction in its reservation queue. Downstream
dependents block. Therefore AIA-KD overhead is REALIZED in sim_ticks (it is
not an analytical post-hoc adjustment).

Coalesced waiters are also stalled until the same response fires; their
contribution to overhead is the (now - queueTime) per-waiter wait, summed as
`totalCoalescedWaitLatency`.

REPORTING
---------
Per-cluster log block printed by printKernelValidationStats():
  Total memory accesses (validated):  N
  Cache hits (0 latency):             N_hit
  Validation requests (full lat):     N_cold        <- aka smid_validations
    of which DMA-ctrl writes:         N_dma         <- aka smid_validations_dma_ctrl
  Coalesced waits (partial lat):      N_coal
  TOTAL SECURITY OVERHEAD:            X us          <- analytical projection
                                                       (sum of cold + coalesced
                                                       latencies measured by
                                                       the model)
  Unique pages validated (total):     P
  Cache hit rate:                     Y%

The harvester sums TOTAL SECURITY OVERHEAD across all clusters (mobilenetv2
prints it 4 times) into the column `aia_kd_overhead_us`, and surfaces
`smid_validations_dma_ctrl` (cluster sum) as a separate column so reviewers
can see how much of the AIA-KD tax is attributable to DMA-engine
reprogramming vs. ordinary first-touch validation.

DMA-CTRL EXCEPTION (DMA-ENGINE REPROGRAMMING)
----------------------------------------------
Writes to a DMA engine's PIO control-reg page (src/dst/len triple) are
treated specially: each store pays FULL validation latency, even on a
"cached" page, because every store reprograms the engine to potentially
touch a new physical buffer that the validator has never seen. The cache
bypass is implemented two ways:
  * The SALAM-Configurator emits each DMA's PIO range into
    `clstr.validator.dma_pio_ranges` (NoncoherentDma + StreamDMA).
  * AiaKdValidator::isDmaCtrl(addr) gates `validatedPagesPerProcess.insert`
    AND `pendingValidationPages.insert/erase`, so DMA control-reg pages
    are never cached and never coalesce. Every store is a cold miss.
LLVMInterface counts these stores in `dmaCtrlValidations` and reports them
as the "of which DMA-ctrl writes" sub-line. On nw the counter shows
~16/41 cold misses are DMA reprogramming (the rest are first-touch tax
on the kernel's working set).

MODELLING CAVEATS (FOR THREATS-TO-VALIDITY / METHODOLOGY)
---------------------------------------------------------
* The GIC IRQ raise is deliberately SUPPRESSED in code (see comment in
  llvm_interface.cc::sendValidationRequest). The bare-metal benchmarks ship
  a stub ISR; raising a real IRQ would inject DerivO3CPU pipeline jitter
  far larger than the modelled tax. Latency is modelled purely via the
  validator's gem5 responseEvent. Bit-identity of `aia-kd@latency=0`
  vs `plain` (within 0.5 % event-queue noise) confirms the protocol is
  timing-inert at lat=0 -- this is enforced by the sanity suite.
* `validateWithKernel()` always returns true (latency-only model; we are
  not modelling a denial policy). The else-branch panics. The denial
  cleanup path is intentionally absent.
* Page granularity is hard-coded 4 KiB (`addr & ~0xFFFULL`). SALAM accesses
  are word/vector aligned; cross-page accesses validate only the first page.
* KNOWN BUG (CSV population): `printKernelValidationStats()` has no
  early-return guard for disabled modes. In plain and iommu runs it
  prints "TOTAL SECURITY OVERHEAD: 0 us" (once per CU) and harvest.py
  populates `aia_kd_overhead_us = 0.000` instead of `-`. Similarly
  `smid_requests`, `smid_validations`, `smid_validations_dma_ctrl` show
  `0` instead of `-` for those modes. The fix is to add
  `if (!enableKernelValidation) return;` at the top of the function.

5. IOMMU APPROACH -- HOW IT WORKS, WHERE OVERHEAD IS INJECTED
================================================================================

CONCEPT
-------
A hardware translation engine shared by every accelerator master in the
cluster, sized as a CONSTRAINED EDGE-IoT PERIPHERAL SMMU (Cortex-M /
Cortex-A5-class SoC, ~400-500 MHz, DDR3 page-table walk, no walk caches,
single PTW thread, MMU-400-class band, SMMUv2 IHI 0062 reference). Every
memory transaction the accelerator emits -- to DRAM, to SPM, or to register
banks -- crosses this SMMU and pays an IOTLB lookup latency.

STATE (lives on AcceleratorIommu)
---------------------------------
  lru             : list<pageAddr>      -- LRU order (front = MRU)
  set             : set<pageAddr>       -- O(log N) hit test, mirrors lru
  uniquePagesSeen : set<pageAddr>       -- cumulative distinct pages ever translated
  nextReadyTick   : Tick                -- monotonic chip-wide port deadline
  IommuStats group: totalChecks, tlbHits, tlbMisses, uniquePages,
                    totalLatencyTicks

API (single entry point)
------------------------
  Tick translate(uint64_t pageAddr, bool isRead);

  Returns the absolute tick at which the translation completes:
    * Disabled / both lats=0  -> returns curTick() (lat=0 fast-path bypass)
    * IOTLB hit               -> +hit_latency  (default 2 ns)
    * IOTLB miss              -> +miss_latency (default 500 ns), insert with
                                  LRU eviction at capacity
    Then: ready = max(curTick(), nextReadyTick) + lat
          nextReadyTick = ready
  i.e. ONE translation in flight at a time per cluster, serialised through
  one chip-wide port. Sibling CUs' translations queue behind the same
  deadline.

PER-ACCESS PROTOCOL  (src/hwacc/comm_interface.cc)
--------------------------------------------------
The intercept is on the RESPONSE PATH. CommInterface has three PORT TYPES
but five intercept sites; ALL call tryIommuDelay(pkt) before delivering:
  * MemSidePort::recvTimingResp  -- covers ALL three roles:
                                      Local (intra-cluster xbar)
                                      Global (coherency_bus -> DRAM, ACP)
                                      Stream (stream FIFO)
  * SPMPort::recvTimingResp      -- on-chip scratchpad
  * RegPort::recvTimingResp      -- register banks (MMRs)
This is the "all-ports" coverage model: on-cluster and off-cluster
traffic are both translated by the single chip-wide AcceleratorIommu.

tryIommuDelay() does:
  1. iommu->translate(page, isRead) -> ready tick.
  2. If ready > curTick(): park pkt on `pendingIommuResps`, schedule (or
     reschedule earlier) `iommuRespEvent` for `ready`. Return true (the
     packet is held until the IOMMU completes; CU stays waiting).
  3. If ready == curTick() (lat=0 / disabled): return false; the response
     proceeds inline (bit-identical to plain mode).

processIommuRespQueue() is the timer that drains parked packets in order
when their ready ticks arrive, calling recvPacket(pkt) which then notifies
LLVMInterface::readCommit/writeCommit.

WHERE THE OVERHEAD ACTUALLY LANDS IN sim_ticks
----------------------------------------------
Like AIA-KD, the IOMMU is REALIZED in sim_ticks: every parked packet
genuinely defers the response delivery. The accelerator's LLVMInterface
stalls because its load/store has not yet committed. Per-access cost adds up
because translations serialize on `nextReadyTick` -- multiple in-flight
accesses queue, mirroring a single chip-wide SMMU port.

Why response-path placement (not request-path):
  Five earlier attempts deferred the access UPSTREAM of CommInterface (at
  launchRead/launchWrite or before comm->enqueueRead). All produced
  iommu sim_ticks LOWER than plain (up to -28 % on `nw`). Root cause:
  deferring upstream left `comm` idle while the dependency tracker thought
  memory was busy, so downstream dependents drained earlier than they
  would under real memory wait. Response-path placement is the only
  injection site that yields monotonic, defensible numbers.

Off-cluster DMA-engine egress also goes through the SAME shared SMMU. The
standalone NoncoherentDma and StreamDma engines own a `DmaPort` (not a
CommInterface), so we extended `src/dev/dma_device.{hh,cc}` with
`setIommu()` + `tryIommuDelay()`. The SALAM-Configurator wires the
cluster-shared `clstr.iommu` SimObject onto every DMA engine's `dma`
port, so DMA bursts to DRAM serialize against CommInterface traffic on
the same chip-wide `nextReadyTick` deadline -- matching a centralized
edge-IoT SMMU with one TCU/TBU.

Coverage caveat: SPM-DMA-fill traffic emitted by ScratchpadRequestPort
(scratchpad-internal fills), and IOAcc::MemSidePort traffic from the
legacy hand-coded I/O accelerators, bypass both CommInterface and the
DmaPort intercept and therefore bypass the IOMMU. Standard
LLVMInterface-based accelerators plus their NoncoherentDma / StreamDma
frontends (all benches in our suite) are fully covered. Mention this in
threats-to-validity.

REPORTING
---------
Per-cluster log block printed by printIommuStats():
  Total IOMMU checks:             N         <- iommu_checks (all 5 port types:
                                                CommInterface MemSide Local/
                                                Global/Stream + SPM + Reg,
                                                plus off-cluster DMA bursts)
  IOTLB hits:                     H
  IOTLB misses (page walks):      M
  IOTLB hit rate:                 H/(H+M) %
  TOTAL IOMMU OVERHEAD:           X us      <- analytical projection
                                                (sum of per-access lats)

The harvester sums these across all clusters into:
  iommu_overhead_us       = analytical projection (sum of latencies)
  iommu_checks, iotlb_hits, iotlb_misses, iotlb_hit_rate_pct
  iommu_unique_pages      = cumulative distinct 4 KiB pages translated
                            (from stats.txt AcceleratorIommu.uniquePages;
                            upper-bounded by AIA-KD's validated-page count
                            since IOMMU sees per-packet traffic)

REALISED end-to-end overhead is the simTicks delta vs `plain`, reported as:
  iommu_overhead_pct   in all_modes_overhead.csv  (= delta_pct in deltas.tsv)

DEFAULTS DEFENCE (for the IOMMU configuration paragraph)
--------------------------------------------------------
  iotlb_entries = 8
    Arm MMU-400 TRM: per-TBU micro-TLB is 8 fully-associative entries.
    MMU-500 TBU: 16 entries. Vendor edge-IoT IPs ship 4-32. 8 sits in the
    middle of this band.
  hit_latency = 2 ns
    1 cycle @ 500 MHz SRAM uTLB lookup.
  miss_latency = 500 ns
    4-level AArch64 walk to slow DDR3 (~125 ns/level random row), no walk
    caches, single PTW thread. Lands mid-band of published edge-IoT
    estimates (200 ns - 1 us).

Sensitivity sweeps emitted by `compare-all --iommu-sweep`:
  iotlb_entries  in {8, 16, 32, 64, 256, 2048}      -- TLB-class story
  miss_latency   in {100, 250, 500, 1000} ns        -- walk-cost robustness
  hit_latency    NOT swept by default (>99.9 % hit rate makes hit cost a
                 linear constant; appendix-only two-point check at 2/4 ns
                 is sufficient).

6. WORKED EXAMPLE: mobilenetv2 (USE THIS EXAMPLE IN BOTH SECTIONS)
================================================================================

mobilenetv2 is the only multi-cluster benchmark in the suite. The model is
partitioned into 4 stages, each its own AccCluster with its own pair of
protection SimObjects:

  Cluster      CUs  Members
  ---------    ---  -----------------------------------------------------
  head           4  head_Top, head_NormalConv, head_DWConv, head_PWConv
  body           5  body_top, body_residual, body_PWConv0, body_DWConv,
                    body_PWConv1
  tail           4  tail_Top, tail_PWConv, tail_Reshape, tail_AvgPool
  classifier     2  classifier_Top, classifier_Linear

  Total:        15 CUs, 4 AiaKdValidators, 4 AcceleratorIommus.

The `*_Top` accelerator in each cluster is the orchestrator -- it dispatches
work; the others are kernel CUs. Per-cluster YAML lives under
benchmarks/mobilenetv2/configs/sys_configs/per_cluster/{1,35,75}/ (the
1/35/75 directories are width-multiplier sweeps; same shape, different
data sizes).

AIA-KD ON mobilenetv2
---------------------
* Validated-page cache is PER CLUSTER, not per simulation. A page that
  holds shared input activations and is touched by all four clusters
  pays the 8.367 us first-touch tax FOUR TIMES (once per cluster's
  validator). State this explicitly in the paper.
* `body` is the heaviest case: 5 CUs racing on cold pages. They serialise
  through body.validator's chip-wide FIFO (one IRQ in flight at a time
  per cluster); same-page misses still coalesce for free on
  waitingForPage[page].
* `classifier` (2 CUs) sees barely any cross-CU contention.
* Per-cluster stats appear in stats.txt as
  `system.acccluster_<head|body|tail|classifier>.validator.*`.

IOMMU ON mobilenetv2
--------------------
* Each cluster has its own 8-entry IOTLB and its own nextReadyTick port
  deadline. Pages cached in head.iommu's IOTLB are NOT visible to
  body.iommu's IOTLB. The same physical page can miss in one cluster
  while hitting in another. (Symmetric with AIA-KD's per-cluster cache.)
* Port-contention queueing tax does NOT cross cluster boundaries.
  body's 5 CUs queue against each other on body.iommu; head's 4 CUs queue
  on head.iommu; the two queues don't interact.
* Per-cluster stats appear as `system.acccluster_<name>.iommu.*`.
* Hit rates on mobilenetv2 are >99.99 % at the default 8-entry IOTLB
  because activation tiles fit in a small set of pages -- so the
  per-access tax is essentially the 2 ns hit cost multiplied by access
  count (~10-12 M checks per cluster).

7. NUMBERS TO QUOTE (HEADLINE TABLE)
================================================================================

Two columns from BM_ARM_OUT/run_all/<bench>/all_modes_overhead.csv are the
right paper-grade numbers:

  aia_kd_overhead_pct  = (sim_ticks(aia-kd) - sim_ticks(plain))
                          / sim_ticks(plain) * 100
  iommu_overhead_pct   = same formula, iommu mode

These are REALIZED end-to-end overheads (AIA-KD response event and IOMMU
response-path queue both perturb sim_ticks directly).

The analytical projections from the per-mechanism reporters:
  aia_kd_overhead_us   from "TOTAL SECURITY OVERHEAD"  in run.log (sum)
  iommu_overhead_us    from "TOTAL IOMMU OVERHEAD"     in run.log (sum)
  iommu_proj_us        same as iommu_overhead_us in the pivot CSV.

For Class-A workloads (lenet_a/b/c, stencil2d, bfs) realized ~ analytical.
For Class-B workloads (md_grid, md_knn, spmv, stencil3d) IOMMU is real but
small. For Class-C workloads (nw, mergesort, occasionally fft) DRAM-row
scheduling jitter can dominate -- realized aia-kd overhead may even go
slightly negative on individual streaming benches; this is real
microarchitectural physics, proven non-bug by the lat=0 bit-identity
invariants in the sanity suite. Mention this in the methodology.

DO NOT report the `effective_us` / `effective_delta_pct` columns from
`deltas.tsv` -- they double-count (they add the analytical projection ON
TOP of sim_ticks, which already contains the realized cost).

8. SANITY / CORRECTNESS GUARDS (METHODOLOGY PARAGRAPH)
================================================================================

tests/aia_cda_tests/run_sanity.py (executed after every rebuild) asserts:
  * Every (bench, mode) row appears in summary.tsv.
  * aia-kd reports non-zero overhead at default latency (checkpoints fire).
  * iommu_checks > 0  (the response-path hook fires on all three ports).
  * aia-kd @ latency=0 is within 0.5 % of plain sim_ticks (event-queue
    reordering noise; proves the AIA-KD bookkeeping is timing-inert when
    the kernel-validation cost is zeroed).
  * iommu @ hit=miss=0 is BIT-IDENTICAL to plain sim_ticks (the
    `translate()` early-return guarantees zero perturbation).

The two lat=0 invariants are the structural correctness guarantee that
underwrites every reported number.

9. PAPER STRUCTURE SUGGESTION
================================================================================

A reasonable outline for the two design sections:

  Section X. AIA-KD Approach
    X.1  Threat model & policy   (per-page first-touch validation)
    X.2  Mechanism                (FIFO + chip-wide responseEvent +
                                   per-cluster validated-page cache +
                                   waiter coalescing)
    X.3  gem5 implementation     (AiaKdValidator SimObject + per-CU
                                   protocol on LLVMInterface, where the
                                   stall is realized)
    X.4  Cost model              (cold miss = 8.367 us; coalesced wait =
                                   partial; cache hit = 0; mobilenetv2
                                   pays 4x for cross-cluster shared pages)

  Section Y. IOMMU Approach
    Y.1  Threat model & device   (peripheral SMMU on the accelerator's
                                   master interface)
    Y.2  Mechanism                (8-entry LRU IOTLB + chip-wide PTW port
                                   + per-access translate() with hit/miss
                                   latency)
    Y.3  gem5 implementation     (AcceleratorIommu SimObject +
                                   CommInterface::tryIommuDelay() on all
                                   three response paths; why
                                   response-path injection)
    Y.4  Configuration            (edge-IoT defaults + sensitivity sweeps)

  Section Z. Comparison
    Z.1  Headline overhead table  (aia_kd_overhead_pct vs
                                   iommu_overhead_pct per benchmark)
    Z.2  Analytical vs realized   (where they agree, where DRAM jitter
                                   widens the gap)
    Z.3  mobilenetv2 deep dive    (per-cluster breakdown: why body is
                                   the hot spot, classifier is cold,
                                   shared-page 4x penalty for AIA-KD)
